Containers on Windows

Why Docker on Windows always runs a virtual machine

A container needs a Linux kernel

A container shares the kernel of the machine it runs on
Linux images expect Linux system calls
Windows has its own NT kernel, not Linux

Windows containers exist, but almost every image on Docker Hub is Linux

So Windows runs Linux underneath

Docker Desktop quietly starts a small Linux virtual machine.

WindowsHypervisorLinux VMContainers

Two ways to get that VM: Hyper-V or WSL 2

What is a hypervisor?

Software that runs virtual machines on real hardware
Type 1 runs on the hardware: Hyper-V, KVM, ESXi
Type 2 runs as an app: VirtualBox, VMware Workstation
Needs CPU virtualisation, Intel VT-x or AMD-V, on in BIOS

Hyper-V vs WSL 2

Hyper-V

Windows Pro, Enterprise or Server

A full VM you manage

Docker's older backend

WSL 2

Works on Windows Home too

A real Linux kernel in a light VM

Docker Desktop's default

Why WSL 2 and not WSL 1?

WSL 1 translates Linux calls into Windows calls: no real kernel
WSL 2 runs Microsoft's real Linux kernel
Docker needs namespaces and cgroups, so only WSL 2 works
Keep projects inside the Linux filesystem for speed

Trace it: is virtualisation on?

PS> systeminfo | findstr /i "hyper-v"
Hyper-V Requirements: A hypervisor has been detected.
PS> bcdedit /enum | findstr /i hypervisorlaunchtype
hypervisorlaunchtype    Auto
PS> Get-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform

Task Manager, Performance, CPU: look for Virtualization: Enabled

Trace it: WSL

PS> wsl --version              # WSL and kernel versions
PS> wsl --status               # default distro and version
PS> wsl -l -v
  NAME              STATE      VERSION
* Ubuntu            Running    2
  docker-desktop    Running    2
PS> wsl --shutdown             # stop every WSL VM

Trace it from Docker

$ docker info --format '{{.OperatingSystem}}'

$ docker context ls

Keep the VM in check

The WSL VM takes memory as it needs it. Set a ceiling.

processors=2

Run wsl --shutdown, then start Docker Desktop again to apply

Why does Docker Desktop on Windows need a virtual machine?

  1. Windows is too slow
  2. Linux containers need a Linux kernel
  3. A licence requires it
  4. To save disk space

Containers share the host kernel, and Windows does not have a Linux one.

The project files

nginx-flask-mysql/
├── compose.yaml          # the whole stack
├── backend/
│   ├── Dockerfile        # Python image with the app inside
│   ├── hello.py          # the Flask application
│   └── requirements.txt
├── proxy/
│   ├── Dockerfile        # Nginx image
│   └── conf              # Nginx configuration
└── db/
    └── password.txt      # the database password

compose.yaml: the database

services:
  db:
    image: mariadb:10-focal
    restart: always
    healthcheck:
      test: ['CMD-SHELL', 'mysqladmin ping -h 127.0.0.1 --password=... --silent']
      interval: 3s
    secrets: [db-password]
    volumes: ["db-data:/var/lib/mysql"]
    networks: [backnet]
    environment:
      - MYSQL_DATABASE=example
      - MYSQL_ROOT_PASSWORD_FILE=/run/secrets/db-password

compose.yaml: backend and proxy

  backend:
    build: { context: backend, target: builder }
    restart: always
    secrets: [db-password]
    ports: ["8000:8000"]
    networks: [backnet, frontnet]
    depends_on:
      db: { condition: service_healthy }
  proxy:
    build: proxy
    restart: always
    ports: ["80:80"]
    networks: [frontnet]
secrets:
  db-password: { file: db/password.txt }

Three details worth noticing

Two networksThe proxy can never reach the database
SecretsThe password is a file, not an environment variable
HealthcheckThe backend waits until the database is ready

The backend image

FROM python:3.10-alpine AS builder
WORKDIR /code
COPY requirements.txt /code
RUN --mount=type=cache,target=/root/.cache/pip pip3 install -r requirements.txt
COPY . .
ENV FLASK_APP hello.py
ENV FLASK_RUN_PORT 8000
ENV FLASK_RUN_HOST 0.0.0.0
CMD ["flask", "run"]

The code is copied into the image: every change needs a rebuild

What the app does

Reads the password from /run/secrets/db-password
Connects to the host named db
On the first request, creates a blog table with four posts
Returns the post titles as HTML

The proxy

Two lines of Dockerfile: FROM nginx, then copy this file in.

server {
    listen       80;
    server_name  localhost;
    location / {
        proxy_pass   http://backend:8000;

Build without installing

Create and run projects with tools that live only in containers

Your machine needs only Docker

Python, Node, database clients: all of them run as throwaway containers.

The whole team uses the same versions
Nothing to uninstall or upgrade later
Works the same on Windows, Linux and macOS

The pattern: mount, work, remove

$ docker run --rm -it \
    -v "$PWD":/work:Z -w /work \
    python:3.13-slim bash
--rmDelete the container on exit
-v "$PWD":/work:ZShare this folder, with an SELinux label
-w /workStart inside that folder

Walkthrough: a new Django project

$ mkdir mysite && cd mysite
$ docker run --rm -v "$PWD":/work:Z -w /work python:3.13-slim \
    sh -c "pip install -q django && django-admin startproject mysite ."
$ sudo chown -R $USER: .      # files were created by root
$ ls
manage.py  mysite

Walkthrough: run it with Compose

services:
  web:
    image: python:3.13-slim
    working_dir: /work
    volumes: ["./:/work:Z"]
    ports: ["8000:8000"]
    command: sh -c "pip install -q django && python manage.py runserver 0.0.0.0:8000"
$ docker compose up -d
$ curl -I http://localhost:8000

$ docker run --rm -v "$PWD":/app:Z -w /app node:24-slim npm init -y

Git and automation

Basic Git, a deploy script, webhooks and GitHub Actions

Git in one slide

$ git clone URL         # copy a repository
$ git status            # what changed?
$ git add .             # stage the changes
$ git commit -m "feat: welcome message"
$ git push              # send to the server
$ git pull              # get the latest

Make the sample your own repo

$ cd /opt/blog-app
$ git init -b main
$ printf 'logs/\ndb/password.txt\n' > .gitignore
$ git config --global user.name "Your Name"
$ git add . && git commit -m "feat: blog app from awesome-compose"
$ git remote add origin https://github.com/YOUR_USER/blog-app.git
$ git push -u origin main

.gitignore keeps the password out of Git. GitHub asks for a token, not a password.

Branches: never push to main

$ git switch -c feat/welcome
$ git commit -am "feat: welcome message"
$ git push -u origin feat/welcome
# then open a Pull Request into main on GitHub

AMS follows the same rule: every change arrives as a pull request

Look before you deploy

$ git log --oneline --graph -10
$ git fetch
$ git diff HEAD origin/main --stat
$ git tag v1.0 && git push --tags

Undo safely

$ git restore backend/hello.py         # drop local edits to a file
$ git revert HEAD                      # new commit that undoes the last
$ git reset --hard origin/main         # server: match the remote exactly

reset --hard throws away local changes. Never edit code on the server.

deploy.sh

#!/bin/bash
set -e
cd /opt/blog-app
mkdir -p logs
exec > >(tee -a "logs/deploy-$(date +%F-%H%M%S).log") 2>&1
echo "=== Deploy started at $(date) ==="
git pull --ff-only
docker compose up -d --build
docker image prune -f
echo "Deploy complete."

What is a webhook?

An HTTP request the Git server sends when something happens.

git pushGitHubHTTP POST
proxy /hooks/webhook :9000deploy.sh

hooks.json

[{
  "id": "deploy-blog",
  "execute-command": "/opt/blog-app/deploy.sh",
  "command-working-directory": "/opt/blog-app",
  "trigger-rule": { "and": [
    { "match": { "type": "payload-hmac-sha256", "secret": "WEBHOOK_SECRET",
        "parameter": { "source": "header", "name": "X-Hub-Signature-256" } } },
    { "match": { "type": "value", "value": "refs/heads/main",
        "parameter": { "source": "payload", "name": "ref" } } }
  ] }
}]

Only signed pushes to main trigger a deploy

The listener as a service

[Unit]
Description=Webhook listener for blog-app
After=network-online.target docker.service
[Service]
ExecStart=/usr/local/bin/webhook -hooks /etc/webhook/hooks.json -port 9000 -verbose
Restart=always
[Install]
WantedBy=multi-user.target
$ sudo systemctl enable --now webhook

Route /hooks/ through the proxy

    location /hooks/ {
        proxy_pass   http://host.docker.internal:9000;
    }
    extra_hosts: ["host.docker.internal:host-gateway"]
$ docker compose up -d --build proxy

Test it from the server

$ curl -X POST http://localhost/hooks/deploy-blog
Hook rules were not satisfied.
$ BODY='{"ref":"refs/heads/main"}'
$ SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" | cut -d' ' -f2)
$ curl -X POST http://localhost/hooks/deploy-blog \
    -H "X-Hub-Signature-256: sha256=$SIG" -H "Content-Type: application/json" -d "$BODY"

Add the webhook on GitHub

Repository, Settings, Webhooks, Add webhook
Payload URL: http://SERVER/hooks/deploy-blog
Content type: application/json, same secret
Events: just the push event

GitHub must reach that URL from the internet. An internal Gitea can reach internal servers.

GitHub Actions

A workflow is a YAML file in .github/workflows
It runs on events: push, pull request, schedule
Jobs run on runners: GitHub's cloud or your own server

A workflow for blog-app

name: Deploy blog-app
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: printf 'ci-only' > db/password.txt
      - run: docker compose build
  deploy:
    needs: build
    runs-on: self-hosted
    steps:
      - run: /opt/blog-app/deploy.sh

A self-hosted runner

# GitHub: Settings, Actions, Runners, New self-hosted runner
$ mkdir actions-runner && cd actions-runner
# download the runner with the commands GitHub shows, then
$ ./config.sh --url https://github.com/YOUR_USER/blog-app --token TOKEN
$ sudo ./svc.sh install && sudo ./svc.sh start

The runner connects out to GitHub: no inbound port needed

Common problems

Port 80 in useStop the host's httpd, or map 8080:80
Access deniedPassword changed after the first start
Secret not foundCreate db/password.txt on the server
502 Bad GatewayBackend down: docker compose logs backend
Change not liveThe code is in the image: up -d --build

A gotcha: the password file

The app reads the file exactly, newline included
MariaDB sets the password only when the volume is empty
Editing password.txt later breaks the login

Change it inside MariaDB with ALTER USER, then update the file

Removing things

$ docker compose stop backend           # stop, keep the containers
$ docker compose rm -sf proxy           # stop and remove one service
$ docker compose down                   # remove containers and networks
$ docker compose down -v                # ...and the volumes: database gone
$ docker compose down --rmi local       # ...and the images we built

Cleaning up disk

$ docker system df                    # what uses the space
$ docker image prune -a               # unused images
$ docker builder prune                # build cache
$ docker volume ls
$ docker volume rm blog-app_db-data   # every record, gone

Why removing hurts

down -v deletes the database, with no confirmation
The next start makes a new, empty database
Rebuilding images means minutes of downtime
After down, nothing comes back on a reboot

Back up before you remove

$ docker compose exec -T db sh -c \
    'mariadb-dump -uroot -p"$(cat /run/secrets/db-password)" example' > backup.sql
$ cp db/password.txt backups/
# restore
$ docker compose exec -T db sh -c \
    'mariadb -uroot -p"$(cat /run/secrets/db-password)" example' < backup.sql

Who brings it back after a reboot?

restart: alwaysYes, if the docker service is enabled
No restart policyNo, it stays stopped
PodmanOnly if podman-restart is enabled
After downNo, the containers are gone

Fix 1: restart policies

  backend:
    restart: always       # or unless-stopped
  proxy:
    restart: always
$ sudo systemctl enable docker            # Podman: enable podman-restart

Fix 2: a service for the stack

[Unit]
Description=blog-app containers
Requires=docker.service
After=docker.service network-online.target
[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/blog-app
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down
[Install]
WantedBy=multi-user.target

Use the service

$ sudo systemctl daemon-reload
$ sudo systemctl enable --now blog-app
$ systemctl status blog-app
$ sudo reboot     # then: docker compose ps

On Podman, Quadlet files in /etc/containers/systemd do the same job

Subdomains

One address for every build, named by its image ID

One server, many versions

Every build gets its own address, like 3f2a1c9b8d7e.apps.example.in

Test a change before it replaces production
Keep the previous version one URL away
The image ID names the container and the subdomain

Step 1: wildcard DNS

*.apps.example.in.    A    10.10.1.20

Every name under apps.example.in reaches the server. Without DNS, test with curl -H "Host: ...".

Step 2: build two versions

$ printf 'FROM nginx:alpine\nCOPY index.html /usr/share/nginx/html/\n' > Dockerfile
$ echo "Version 1" > index.html && docker build -t site:v1 .
$ echo "Version 2" > index.html && docker build -t site:v2 .
$ docker images site
REPOSITORY   TAG   IMAGE ID       CREATED
site         v2    7c41d0e2a9b3   5 seconds ago
site         v1    3f2a1c9b8d7e   20 seconds ago

Step 3: a container per image ID

$ docker network create apps
$ for t in v1 v2; do
    id=$(docker images -q site:$t)
    docker run -d --name site-$id --network apps site:$t
  done
$ docker ps --format '{{.Names}}'
site-7c41d0e2a9b3
site-3f2a1c9b8d7e

Step 4: route by subdomain

server {
  listen 80;
  server_name ~^(?<id>[a-f0-9]{12})\.apps\.example\.in$;
  resolver 127.0.0.11 valid=10s;      # Docker's internal DNS
  location / {
    proxy_pass http://site-$id;
    proxy_set_header Host $host;
  }
}

Step 5: start the router and test

$ docker run -d --name router --network apps -p 8081:80 \
    -v "$PWD"/router.conf:/etc/nginx/conf.d/default.conf:Z nginx:alpine
$ curl -H "Host: 3f2a1c9b8d7e.apps.example.in" http://localhost:8081

For Django: allow the subdomains

ALLOWED_HOSTS=.apps.example.in
CSRF_TRUSTED_ORIGINS=https://*.apps.example.in

A leading dot in ALLOWED_HOSTS matches every subdomain

Roll back by ID

$ docker images --format '{{.ID}}  {{.Tag}}  {{.CreatedSince}}' site
$ docker rm -f site-7c41d0e2a9b3       # drop the bad version
# 3f2a1c9b8d7e.apps.example.in still serves v1
$ docker image prune                   # tidy up later

Which command deletes the database volume?

  1. docker compose ps
  2. docker compose down -v
  3. docker compose logs
  4. docker compose restart

-v removes named volumes. Take a backup first.

What brings the app back after the server reboots?

  1. git pull
  2. docker compose logs
  3. A systemd service or restart policy
  4. A bigger disk

Restart policies plus an enabled engine, or blog-app.service.

What does a wildcard record like *.apps.example.in do?

  1. Sends every subdomain to one server
  2. Blocks all subdomains
  3. Deletes old images
  4. Encrypts the traffic

Nginx then decides which container answers each name.

Key takeaways

On Windows, Linux containers run in WSL 2 or Hyper-V
On Oracle Linux, they use the server's own kernel
One compose file runs the proxy, the app and the database
Push to main, then a webhook or Actions runs deploy.sh
Back up before down -v, and use a service for reboots
Image IDs plus subdomains give previews and rollback
